# Модель угроз и безопасность AETHER MAIL

Это рабочий документ по текущему ядру (docker-mailserver + панель). Он описывает реализованные меры и известные ограничения. Система не является «абсолютно защищённой» — список ограничений в конце.

## Активы

- Пароли почтовых ящиков (Dovecot хранит их хешированными).
- Приватные ключи DKIM в `./config`.
- SSL-ключи в `./certs`.
- Пароль администратора панели (только PBKDF2-хеш в `.env.panel`).
- Содержимое писем пользователей в `./data/mail`.

## Модель угроз (кратко)

| Угроза | Мера в текущем ядре |
|--------|---------------------|
| Подбор пароля панели | PBKDF2-хеш; 5 попыток → блокировка на 60 с по IP; задержка 0,7 с на неверный пароль; прунинг счётчика |
| Подбор пароля ящика | Fail2ban на SMTP; панель не даёт тестировать пароли ящиков (отправка — только с реальным паролем) |
| CSRF | HMAC-подписанный токен на каждой форме, проверка на сервере |
| XSS | Все строки пользователя проходят HTML-экранирование (`esc`) перед выводом; CSP запрещает внешние скрипты |
| Session fixation / перехват | Случайный `PANEL_SESSION_SECRET`, cookie `HttpOnly + SameSite=Lax + Secure`, отдельный от хеша пароля |
| Open relay | docker-mailserver по умолчанию требует авторизации для отправки; подтверждено тестом `swaks`/telnet на :25 без AUTH → 554 |
| Подмена отправителя | SPF, DKIM-подпись исходящих, DMARC `p=quarantine` — настройка DNS описана в панели (`/dns`) |
| Компрометация сервера | ufw: наружу только нужные порты; SSH на 22; обновления — `apt upgrade` + `docker compose pull` периодически |
| Утечка через git | `.gitignore` на `.env*`, `certs/`, `config/`, `data/`; CI проверяет отсутствие секретов |
| Сниффинг | TLS 1.2/1.3 на панели и SMTP; HSTS не добавлен — см. ограничения |

## Что фиксируется для расследований

- Fail2ban пишет баны в `data/mail-state/log` и свой журнал.
- Postfix логирует подключения и попытки AUTH в `data/mail-state/mail.log` (через `docker compose logs mailserver`).
- Панель не логирует содержимое писем и пароли; ошибки SMTP показываются только администратору в интерфейсе.

Централизованный аудит-воркер и панель событий безопасности — в дорожной карте (спецификация §6, §11).

## Известные ограничения (честный список)

1. **HSTS** не включён в nginx: если домен ещё может обслуживаться по HTTP где-то, преждевременный HSTS сломает доступ. Включи `add_header Strict-Transport-Security "max-age=31536000" always;` когда убедишься, что весь домен работает по HTTPS.
2. **Docker-соккет в панели** даёт контейнеру root-эквивалент на хосте. Компенсирующая мера: образ собирается из своего Dockerfile (никаких `latest`-образов с соккетом), панель недоступна извне в обход nginx. Правильное решение — выделенный API-адаптер с минимальным набором команд (дорожная карта §1).
3. **ClamAV выключен** (`ENABLE_CLAMAV=0`) — антивирусной проверки вложений нет. Включение требует ~1 ГБ RAM. До включения — Rust mime-worker в спецификации.
4. **Нет rate-limit на отправку писем из панели** — администратор может случайно/злонамеренно отправить много писем. Лимиты Postfix (`smtpd_client_message_rate_limit` и т.п.) не настраивались отдельно.
5. **Панель — единственная точка администрирования**, одна роль (admin). Роли и MFA — в спецификации §4, §11.
6. **Резервные копии шифруются, но ключ шифрования лежит рядом с бэкапом** при настройке «по умолчанию» — храни ключ отдельно (`BACKUP_PASSPHRASE_FILE`).

## Реагирование на инцидент

1. Отзови доступ: смени пароль панели (`setup email update admin@…` не поможет — перегенерируй `.env.panel`: `PANEL_ADMIN_HASH` и `PANEL_SESSION_SECRET`), перезапусти `docker compose up -d`.
2. Проверь баны и логи: `docker compose logs mailserver | grep -i "fail\|auth"`, `docker exec mailserver fail2ban-client status`.
3. Смени пароли всех ящиков через панель или `setup email update`.
4. Если компрометирован сервер — смотри INCIDENT-процедуру в дорожной карте; настоящий ответ — восстановление из чистого бэкапа на чистый хост.
